# CLAUDE.md

This repository is the source of **Factory**, a Claude Code skill that runs a coding task through a small team of agents: a planner that writes specs, one implementer per spec that writes the tests first and then the code, one QA agent per spec that checks the spec afterwards, a checker, and independent reviewers (one for the whole change, plus one per spec when the work was split). There is no repair phase: a spec QA or review fails goes back to Build, to a fresh implementer session and QA again, as a card goes back to Ready on super-board. The team is orchestrated by code (a Workflow script), not by an agent following instructions. It is being rebuilt from scratch, starting from a deliberately small baseline. Two prose skills come before it when the work is tracked in GitHub issues: `ba-ticket` turns a task into issues (one issue is one run and one pull request) and `dev-subissues` adds sub-issues that are context for the planner only; the issue's criteria are the contract, and an issue run ends in a pull request merged into the default branch. See [README.md](README.md) for the user-facing description.

## Layout

- `ba-ticket/`, `dev-subissues/`: the BA and developer skills that write the issue and its sub-issues, each with a template under `references/`. They are separate skills, not part of the team, and are installed next to `factory` in `~/.claude/skills`. The issue template's criteria `C1..Cn` and out-of-scope section are what `factory/SKILL.md` reads into the contract, so change them together.
- `ui-refine-loop/`: a standalone skill that polishes the look of one existing page or component in bounded check → fix rounds and ends in a draft pull request it never merges. Adapted on 2026-11-16 from super-board's `ui-refine-loop` (MIT, `NOTICE.md` names the commit and what changed), and vendored rather than installed, because the original leans on super-board's config, writing standard and a workflow outside the skill folder. It is installed next to `factory` in `~/.claude/skills` (on this machine as a symlink to this folder, like the others), is not part of the team and is not in the `SKILLS` registry: its first step asks the user questions, and nobody answers during a factory run. `SKILL.md` instructs the invoking session; `workflow/ui-refine-loop.js` runs the rounds (design reviewer and detector in isolation, checker, fixer, a finish reviewer at the end) and owns the stop rules; `references/` holds the agents' briefs, which the script names by path, so rename them together; `scripts/` sets up the worktree and dev server, takes the screenshots and builds the Before | After table. Project settings come from `.claude/ui-refine-loop.json` in the project being refined. It uses the Impeccable skill when installed and a built-in rubric, loudly, when not. Its agents run on the session's model: no per-role models were chosen for it.
- `pr-judge/`: a standalone skill (added 2026-11-17, chosen with the user) that judges one pull request against the issue it closes, from outside the team: measured checks (`scripts/prepare.ts`: `gh`, worktrees for head and merge base, build, type check, lint, format and tests with the base's commands, dependencies added, code without a test, shortcuts around the checks, optional SonarQube), then one isolated judge per section of `rubric.md`, started by the invoking session, and `scripts/assemble.ts` for the report and the verdict. Like `ui-refine-loop` it is installed next to `factory` (here as a symlink), is not part of the team and is not in the `SKILLS` registry. **Keep it independent of the team**: it must not load any skill the `SKILLS` registry lists, and no role brief or script of the team may call it or read its rubric, or the team would be tuned to its grader. `rubric.md` and the verdict rule (`verdictOf` in `scripts/lib.ts`) are owned by the user, like a grader: change them only when the user asks, and bump `RUBRIC_VERSION` with every change to a question, an anchor or the rule. The scripts are TypeScript run by Node's type stripping, with no package imports. It sends its report to XS Factory Bench with `xfb judge send` (a `judge.report` event defined in that repository's `packages/contract`), so a change to `report.json`'s fields is made there too.
- `factory/SKILL.md`: instructions for the invoking session. It writes the contract with the user, puts the run on its own branch, starts the workflow, reruns the checks itself, merges a passing run into the branch it started from (an issue run: pushes, opens a pull request closing the issue and its sub-issues, and merges it into the default branch), looks for failures that recur across runs and proposes lessons, and reports.
- `factory/workflow/factory.js`: the Workflow script. It runs Spec, Build (each spec: implementer, then QA, back to the implementer while QA fails), Check and Review, sends the specs a failure concerns back to Build, validates specs, orders them by dependency, decides pass or fail from the raw results, and logs every failure that sent a spec back.
- `factory/scripts/`: shell scripts the invoking session runs: `skills-ready.sh` resolves the skills the team loads to installed SKILL.md files for the `skills` arg (exit 10 names the missing ones), `install-skills.sh` installs them from their own repositories at pinned commits, and the `factorybench-*` files report a run to FactoryBench.
- `factory/roles/*.md`: one brief per role (planner, implementer, qa, checker, reviewer, spec-reviewer). The script tells each agent to read its brief; the paths are passed in through `args`.
- `factory/evals/<case-name>/`: test cases in the `claude plugin eval` layout (prompt, starting files, graders).
- `factory/dashboard/`: a static page for people, shipped with the skill. `index.html` shows the team, the rules the script enforces, per-phase progress of each run and the benchmark, and opens straight from disk. It reads finished runs from `runs.js` (the invoking session appends one after each run; the field list is at the top of that file), the lessons from `lessons.js` and the run in progress from `live.js`, which it reloads every few seconds. `live.js` is git-ignored: the script builds each progress record itself (`runRecord`) and, because it cannot write files, has a small recorder agent overwrite the file at each barrier of the run, when the `dashboard` arg is passed. The recorder is not a team role and has no brief. The page's roles, flow and rules are written out by hand, so update them when the team or the script changes.
- **Lessons** (since 2026-11-16, chosen with the user): code files every failure that sent a spec back to Build, or ended the run, in the run record's `failureLog` (`failureEntries`). After each run the invoking session (SKILL.md, step 7) reads the logs of the last 10 runs, and a mistake made in 3 or more runs becomes a `proposed` entry in `dashboard/lessons.js` and a proposal in its report: a rule in `factory.js` when code can decide it, otherwise one sentence in a role brief. The user accepts or rejects it; an accepted lesson is made in this repository as an ordinary change with its test, and set to `done` there. No agent of the team and no factory run ever edits the skill: the team's rules are the user's decision, and the skill is a symlink shared by every session. `failureLog` is also sent to XS Factory Bench (`~/Documents/xs-factory-bench`, a separate repository that parses the run record in `packages/core/factory/run-record.ts`), so a change to its fields is made there too.
- `tests/`: `node --test` tests for the pure helpers of `factory.js`. Not part of the skill.
- `factory-workspace/`: test run outputs, created on demand next to the skill. Disposable and git-ignored; never part of the skill.

## How to work here

- **Code owns the skeleton, agents own the judgment.** Anything that can be decided mechanically (order, parallelism, what an agent is shown, spec validation, the rebuild cap, pass or fail) belongs in `factory.js`, not in prose that an agent might not follow. Prose is for what needs judgment: writing the contract, splitting a task into specs, reviewing code.
- **Keep the script and the briefs in step.** The JSON schemas in `factory.js` define what each agent returns; the "Return" section of each role brief describes the same fields. Change both together, and update the `args` example in `SKILL.md` when the script's inputs change.
- **Workflow scripts are restricted.** Plain JavaScript only, starting with `export const meta = {...}` as a pure literal. No filesystem, shell or Node APIs, and no `Date.now()`, `Math.random()` or argless `new Date()`. That is why checks are run by a checker agent and role briefs are read by the agents themselves. Load the `workflow-authoring` skill before changing the script.
- **Grow from the baseline in small steps.** Add machinery (a ledger, per-task modes, a dashboard) only when the user asks for it or a test shows the loop needs it. Do not port pieces of the old suite back in on your own initiative.
- **Skill and role text is a prompt, not documentation.** Write it for the agent that will read it: imperative, lean, and with the reason behind each rule so the agent can apply it to cases the text did not foresee.
- **Keep the roles independent.** The value of the team is fresh context. One spec, one agent, one session: an implementer sees only its own spec, and no agent is ever handed several specs. The implementer writes each test before its code and sees it fail (TDD, after super-board's builder lane); because those tests come from the agent that wrote the code, a QA agent then reads them against the spec in a fresh session, without the spec's planned `changes` or the implementer's account, writes tests for the serious gaps in the spec's test files only, runs the security pass, and lists what the code or tests must answer for (after super-board's Tester lane). Whatever QA or review fails goes back to Build: QA's failures send its spec back at once, and `routeFailures` sends each check or review failure to the spec whose files it concerns; that spec's implementer is started again in a fresh session with its spec, its failures and the other parts' interfaces, then QA checks it again, at most `maxRebuilds` times per spec. The implementer may change its own source and test files, and code records every test file changed after the first build so the session reports it. Every agent of the team is given a scratch directory of its own (`scratchDir`, under the `scratch` root next to the repository), because agents of one run otherwise share their session's scratchpad and can delete each other's files or write through a link another made into the repository. A spec reviewer sees one spec and its files; the whole-change reviewer sees the contract, the diff, the check results and the interfaces between specs; no reviewer sees an implementer's or QA agent's narrative; no file has two owners across specs.
- **Models are chosen per role in code.** The `MODELS` table in `factory.js` gives each role its model and effort (planner Fable/high and whole-change reviewer Opus/high, because a mistake there costs the most; implementers, QA, spec reviewers Sonnet/medium; a spec sent back to Build rebuilt on Opus; the checker Sonnet/low), chosen with the user on 2026-11-14. The `models` arg overrides entries, which is how to A/B a change before making it the default.
- **Skills the team loads are installed, not bundled.** Since 2026-11-14 the user chose super-board's model: the implementers, QA agents and reviewers load third-party skills through the Skill tool, picked by the `SKILLS` registry in `factory.js`, which follows super-board's skill registry row for row: build rows by the spec's `kind`, fixed skills per role (QA: tdd, diagnosing-bugs, verification-before-completion, testing-strategy, mp-code-review, pr-security-review), and a conditional tier with a rule each (vitest, playwright-best-practices, testing-strategy, domain-modeling for implementers; vitest, playwright-best-practices for QA); a run starts without the conditional ones. Sources: mattpocock/skills, obra/superpowers, EricTechPro/super-board, antfu/skills, anthropics/knowledge-work-plugins, currents-dev. The README carries a prompt people paste into Claude Code to install Factory and these skills; keep it in step with the scripts. They are installed into `~/.claude/skills` by `scripts/install-skills.sh` (pinned commits, never overwriting) and resolved before each run by `scripts/skills-ready.sh`, whose `REQUIRED` and `OPTIONAL` lists must match the registry (a test checks it). Do not copy their text into the briefs. Anything else that requires writing to `~/.claude/` (for example custom agent definitions) is still a design change to raise with the user first.
- **Skill, role and script files are in English.** `README.md` is in English too; keep it, and its screenshots in `docs/images/`, in sync when the team, the flow or the layout changes.

## Testing

- **Script logic**: the helpers at the top of `factory.js` (`validateSpecs`, `buildLevels`, `matchesIgnore`, `filesOutsideOwnership`, `filesOutsideAssignment`, `testsChanged`, `skillsFor`, `missingSkills`, `conditionalFor`, `modelFor`, `modelProblems`, `evaluate`, `routeFailures`, `failureEntries`, `runRecord`, `specText`, `issueText`, `scratchDir`) are pure functions, tested in `tests/` at the repository root (outside the skill, so it is not shipped with it). Run `node --test` from the root after changing them, and add a test with every new rule. `tests/skills.test.mjs` runs `skills-ready.sh` with `bash` against scratch skill directories. `tests/load.mjs` evaluates the part of the file above the "The run" section and hands the helpers back; add a new helper's name to its list. For a syntax check, wrap the whole file in an `async function` and run `node --check`, since the body uses top-level `return`.
- **ui-refine-loop**: `tests/ui-refine-workflow.test.mjs` runs the whole workflow script with `agent`, `phase` and `log` stubbed (stop rules, routing, what each agent is shown, the score), which is also its syntax check; `tests/ui-refine-setup.test.mjs` runs `refine-setup.sh detect`, the helpers of `shoot.mjs` and `pr-shots.sh` against scratch directories, with no dev server and no browser. A real run costs about four agents per round, so confirm with the user first.
- **pr-judge**: `tests/pr-judge.test.ts` tests the pure helpers of `pr-judge/scripts/lib.ts` (diff reading, shortcuts, manifests, acceptance criteria, merging the judges' answers, the verdict rule, the report). `prepare.ts` and `assemble.ts` need `gh` and a real pull request; a full run starts 8 judge agents, so confirm with the user first.
- **End to end**: copy an eval case's `files/` into a scratch directory, `git init` and commit it, then run the workflow against it. A run starts at least five agents (one spec with tests), and 3N+3 for N specs before any return to Build; each return of a spec to Build adds an implementer and a QA agent, and a return from review adds a checker and the reviewers. One small recorder agent per step is added when `dashboard` is passed. Confirm with the user before running more than one.
- **Skill evals**: use the `skill-creator` skill's workflow with the cases in `factory/evals/`, saving results under `factory-workspace/iteration-N/`.

## Boundaries

- This skill is installed on this machine as a symlink: `~/.claude/skills/factory` points at the `factory/` folder of this working copy. Every edit here, and every branch switch, changes the skill that all Claude Code sessions use, including runs in other projects, which also write `dashboard/live.js` and `dashboard/runs.js` here. The older Factory suite (the `factory-*` skills and the `factory-*` agents) was removed on 2026-11-13; do not bring it back unless the user asks.
- Untracked and ignored files (for example `factory-workspace/`) are not recoverable through git, so move them to the Trash instead of removing them outright, and look at the target first.
- Commit or push only when the user asks.
