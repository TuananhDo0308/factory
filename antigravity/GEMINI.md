# GEMINI.md

This repository is the source of **Factory**, a Gemini Antigravity skill suite that runs a coding task through a small team of agents: a planner that writes specs, one implementer per spec that writes the tests first and then the code, one QA agent per spec that checks the spec afterwards, a checker, independent reviewers (one for the whole change, plus one per spec when the work was split), and a QC agent that uses the product. There is no repair phase: a spec QA, review, or QC fails goes back to Build, to a fresh implementer session and QA again, as a card goes back to Ready on super-board. The team is orchestrated by code (a Python `run_workflow` script), not by an agent following instructions. Two prose skills come before it when the work is tracked in GitHub issues: `ba-ticket` turns a task into issues (one issue is one run and one pull request) and `dev-subissues` adds sub-issues that are context for the planner only; the issue's criteria are the contract, and an issue run ends in a pull request merged into the default branch. See [README.md](README.md) for the user-facing description.

## Layout

- `ba-ticket/`, `dev-subissues/`: the BA and developer skills that write the issue and its sub-issues, each with a template under `references/`. They are separate skills, not part of the team, and are installed next to `factory` in `~/.gemini/config/skills`. The issue template's criteria `C1..Cn` and out-of-scope section are what `factory/SKILL.md` reads into the contract, so change them together.
- `ui-refine-loop/`: a standalone skill that polishes the look of one existing page or component in bounded check → fix rounds and ends in a draft pull request it never merges. Adapted from super-board's `ui-refine-loop` (MIT, `NOTICE.md` names the commit and what changed), and vendored rather than installed, because the original leans on super-board's config, writing standard and a workflow outside the skill folder. It is installed next to `factory` in `~/.gemini/config/skills`, is not part of the team and is not in the `SKILLS` registry: its first step asks the user questions, and nobody answers during a factory run. `SKILL.md` instructs the invoking session; `workflow/ui-refine-loop.py` runs the rounds (design reviewer and detector in isolation, checker, fixer, a finish reviewer at the end) via `run_workflow` and owns the stop rules; `references/` holds the agents' briefs, which the script names by path, so rename them together; `scripts/` sets up the worktree (`.agents/worktrees/refine-<slug>`) and dev server, takes the screenshots and builds the Before | After table. Project settings come from `.agents/ui-refine-loop.json` (or `.gemini/ui-refine-loop.json`) in the project being refined. It uses the Impeccable skill when installed and a built-in rubric, loudly, when not. Its agents run on the session's model: no per-role models were chosen for it.
- `pr-judge/`: a standalone skill that judges one pull request against the issue it closes, from outside the team: measured checks (`scripts/prepare.ts`: `gh`, worktrees for head and merge base, build, type check, lint, format and tests with the base's commands, dependencies added, code without a test, shortcuts around the checks, optional SonarQube), then one isolated subagent per section of `rubric.md`, started by the invoking session via `invoke_subagent`, and `scripts/assemble.ts` for the report and the verdict. Like `ui-refine-loop` it is installed next to `factory`, is not part of the team and is not in the `SKILLS` registry. **Keep it independent of the team**: it must not load any skill the `SKILLS` registry lists, and no role brief or script of the team may call it or read its rubric, or the team would be tuned to its grader. `rubric.md` and the verdict rule (`verdictOf` in `scripts/lib.ts`) are owned by the user, like a grader: change them only when the user asks, and bump `RUBRIC_VERSION` with every change to a question, an anchor or the rule. The scripts are TypeScript run by Node's type stripping, with no package imports.
- `factory-init/`: the one-time setup of a project, run in an interactive session with a person, because nobody answers questions during a run. It tells a new project from an existing one (`scripts/detect-stack.mjs`), reads its design (`detect-design.mjs`) and screens (`find-routes.mjs`), catalogues an existing front end from its code (`scan-ui.mjs`: components, props, variants, usage, duplicates with the person's `preferred` choice, pattern files to copy, into `.factory/design/ui-store/catalog.md`; this, not screenshots, is what agents build new screens from), optionally screenshots it for people and QC (`capture-screens.mjs`, which drives `ui-refine-loop/scripts/shoot.mjs`), finds and installs stack skills (`stack-skills.mjs` from `factory/catalog/stack-skills.json`, or `find-skills.mjs` + `stack-skills.mjs add` for one a person read and approved, always at a pinned commit, into the project's `.agents/skills`), lays out `.factory/` (`init-skeleton.mjs`, adding `.agents/plugins/factory-browser/mcp_config.json` with Playwright MCP when the project has a UI) and checks the result (`project-check.mjs`). It starts with `init-status.mjs`, which says in one command, reading no code, whether the project is set up (`none`, `partial`, `stale`, `complete`): each step is marked done in `.factory/init.json` with a fingerprint of the files it was based on (git blob ids of the working tree), so a repeated init stops at once, a stopped one resumes, and a changed project redoes only the steps whose files changed. `.factory/project.json` is the project's profile: the session passes its `projectSkills`, `projectDocs`, `protectedPaths` and `escalate` to the workflow, and its commands become the contract's checks. The pure functions of these scripts are tested in `tests/project-setup.test.mjs`, `tests/init.test.mjs`, `tests/scan-ui.test.mjs` and `tests/init-status.test.mjs`; their `main`s need a repository, `gh` or a browser.
- `factory-clarify/`: the one step between a request (a GitHub issue or the user's own words) and a build. Interactive: it grills the person with recommended answers, writes the ticket by `ba-ticket`'s template and rules, proposes splitting it into several tickets (never sub-issues) when it is more than one pull request, draws every new screen from the app's own components and tokens and screenshots it into `.factory/design/mockups/<n>/`, checks the draft (`ready-check.mjs --body-file`) and runs the planner alone on it until it has no questions, keeps that plan in `.factory/plans/<n>.json`, gets the person's approval, and only then creates or rewrites the issue, pushes the branch `factory/<n>` with the mockups and the plan, and adds `ready` (AI mode). The factory skill sends any request that is not a ready ticket here first, builds on that branch, and reuses the approved specs while the criteria and the files they touch are unchanged.
- **The pipeline around issues**: `ba-ticket` and `dev-subissues` create issues through `factory/scripts/factory-issue.sh`, which labels them `factory` and `kind/<kind>` so they never mix with hand-written ones and only they can be dispatched. `ba-ticket/references/checklists.md` lists what to settle per kind; it grows from `scripts/issue-history.mjs` (questions, stops and regressions of earlier issues) by the user's decision, like lessons. `scripts/ready-check.mjs` is the mechanical readiness check and `scripts/next-issue.mjs` the dispatcher's choice; their pure functions are tested in `tests/`. `factory/github/` holds the GitHub Action template (`agy -p`) for a self-hosted runner and its setup; it reacts to issue events only and leaves pull requests open (`no-merge`). The planner returns `questions` and code stops the run on any (`openQuestions`); `questionsOnly: true` runs the planner alone as the readiness check. The contract's `design` (DESIGN.md, tokens, UI store and an approved mockup per screen, as files in the repository) reaches the planner, the implementer and reviewers of the specs whose criteria show those screens (`design_text`), and QC, which compares each screen with its mockup (`screens` in its result; a difference goes back to Build like a failed criterion). Correctness rules: a check that fails and passes when the checker reruns it is flaky (`flaky_checks`), reported and not sent back; when the contract has a `testFileCommand`, the checker runs each feature, bug or UX spec's test files on the base code in a scratch worktree, and tests that pass there send the spec back (`tdd_targets`, `tdd_failures`); a change with a migration is run up, down and up again when the contract has `migration` (`migration_failures`); QC compares the screens in `design.baseline` with before shots the session took on the base commit (a regression goes to the specs owning UI files) and scans each mockup screen for accessibility (a serious or critical violation fails its criteria). Every role but QC is told the stack (`projectStack`). The planner loads `codebase-design` (and may load `domain-modeling`), and every role but the checker is offered the project's own skills under `<repo>/.agents/skills` or `<repo>/.gemini/skills` that it is not already loading (`repo_skills_for`). The gate skips reviewers and QC while any check fails; the planner rates `risk` and `surfaces`, `assess_risk` raises them from the specs' files (`SENSITIVE`, `UI_FILES`) and `ROUTING` picks the reviewers and their models; `PROTECTED` lists the check configuration no spec may own or change (`allowProtected` opens it for a run about it); and `escalation` decides from the changed files, the risk and the rewritten tests whether a passing run may merge without a person (`merge` in the result).
- `factory/SKILL.md`: instructions for the invoking session. It writes the contract with the user, puts the run on its own branch, starts the `run_workflow` script, reruns the checks itself, merges a passing run into the branch it started from (an issue run: pushes, opens a pull request closing the issue and its sub-issues, and merges it into the default branch), looks for failures that recur across runs and proposes lessons, and reports.
- `factory/workflow/factory.py`: the Python `run_workflow` script. It runs Spec, Build (each spec: implementer, then QA, back to the implementer while QA fails), Check, and Review with QC beside it once the checks pass, sends the specs a failure concerns back to Build, validates specs, orders them by dependency, decides pass or fail from the raw results, and logs every failure that sent a spec back.
- `factory/scripts/`: shell and Node scripts the invoking session runs: `skills-ready.sh` resolves the skills the team loads to installed SKILL.md files for the `skills` arg (exit 10 names the missing ones), and `install-skills.sh` installs them from their own repositories at pinned commits.
- `factory/roles/*.md`: one brief per role (planner, implementer, qa, checker, reviewer, spec-reviewer, qc). The script tells each agent to read its brief; the paths are passed in through `args`.
- `factory/evals/<case-name>/`: test cases (prompt, starting files, graders).
- `factory/dashboard/`: a static page for people, shipped with the skill. `index.html` shows the team, the rules the script enforces, per-phase progress of each run and the benchmark, and opens straight from disk. It reads finished runs from `runs.js` (the invoking session appends one after each run; the field list is at the top of that file), the lessons from `lessons.js` and the run in progress from `live.js`, which it reloads every few seconds. `live.js` is git-ignored: `factory.py` builds each progress record itself (`run_record`) and writes `live.js` directly and atomically at each barrier of the run when the `dashboard` arg is passed (no recorder agent needed). The page's roles, flow and rules are written out by hand, so update them when the team or the script changes.
- **Lessons**: code files every failure that sent a spec back to Build, or ended the run, in the run record's `failureLog` (`failure_entries`). After each run the invoking session (`SKILL.md`, step 6) reads the logs of the last 10 runs, and a mistake made in 3 or more runs becomes a `proposed` entry in `dashboard/lessons.js` and a proposal in its report: a rule in `factory.py` when code can decide it, otherwise one sentence in a role brief. The user accepts or rejects it; an accepted lesson is made in this repository as an ordinary change with its test, and set to `done` there. No agent of the team and no factory run ever edits the skill: the team's rules are the user's decision, and the skill is often a symlink shared by every session.
- `tests/`: Python `unittest` (`test_factory_helpers.py`, `test_factory_workflow.py`, `test_ui_refine_workflow.py`) and Node `node --test` tests for the scripts, setup helpers, and `pr-judge`. Not part of the skill.
- `factory-workspace/`: test run outputs, created on demand next to the skill. Disposable and git-ignored; never part of the skill.

## How to work here

- **Code owns the skeleton, agents own the judgment.** Anything that can be decided mechanically (order, parallelism, what an agent is shown, spec validation, the rebuild cap, pass or fail) belongs in `factory.py`, not in prose that an agent might not follow. Prose is for what needs judgment: writing the contract, splitting a task into specs, reviewing code.
- **Keep the script and the briefs in step.** The JSON schemas in `factory.py` define what each agent returns; the "Return" section of each role brief describes the same fields. Change both together, and update the `Args` example in `SKILL.md` when the script's inputs change.
- **Workflow scripts run via Antigravity `run_workflow`.** Read the `run-workflow` skill before changing `factory.py` or `ui-refine-loop.py`. Top-level `await` works inside the `run_workflow` Python 3.8+ runner (`args`, `agent`, `parallel`, `pipeline`, `phase`, `log` are injected globals).
- **Grow from the baseline in small steps.** Add machinery (a ledger, per-task modes, a dashboard) only when the user asks for it or a test shows the loop needs it. Do not port pieces of older suites back in on your own initiative.
- **Skill and role text is a prompt, not documentation.** Write it for the agent that will read it: imperative, lean, and with the reason behind each rule so the agent can apply it to cases the text did not foresee.
- **Keep the roles independent.** The value of the team is fresh context. One spec, one agent, one session: an implementer sees only its own spec, and no agent is ever handed several specs. The implementer writes each test before its code and sees it fail (TDD, after super-board's builder lane); because those tests come from the agent that wrote the code, a QA agent then reads them against the spec in a fresh session, without the spec's planned `changes` or the implementer's account, writes tests for the serious gaps in the spec's test files only, runs the security pass, and lists what the code or tests must answer for (after super-board's Tester lane). Whatever QA or review fails goes back to Build: QA's failures send its spec back at once, and `route_failures` sends each check or review failure to the spec whose files it concerns; that spec's implementer is started again in a fresh session with its spec, its failures and the other parts' interfaces, then QA checks it again, at most `maxRebuilds` times per spec. The implementer may change its own source and test files, and code records every test file changed after the first build so the session reports it. Every agent of the team is given a scratch directory of its own (`scratch_dir`, under the `scratch` root next to the repository), because agents of one run otherwise share their session's scratchpad and can delete each other's files or write through a link another made into the repository. A spec reviewer sees one spec and its files; the whole-change reviewer sees the contract, the diff, the check results and the interfaces between specs; no reviewer sees an implementer's or QA agent's narrative; no file has two owners across specs. **QC** is the only role that judges the product rather than its code: once the checks pass, beside the reviewers, it starts the product as the contract's `run` says and tries each criterion through the real entry point, seeing only the contract (`qc_text`: no specs, files, diff or checks). It loads no review skill, so it does not share the reviewers' blind spots, and it changes nothing in the repository. It uses a screen by hand: it clicks and types one step at a time through the browser tools of Playwright MCP (`browser` names the server configured in `.agents/plugins/factory-browser/mcp_config.json` or `~/.gemini/config/mcp_config.json`, which `factory-init` adds, pinned and headless; `browser_note`), writes no browser script and loads no skill for writing browser tests; a run whose change has a screen stops before any agent starts without that server (`needs_browser`, `browser_problem`), and it lists each action in `steps`. **Coding standards**: `factory-init` writes `CODING_STANDARDS.md` from `factory-init/references/coding-standards-template.md`, a table of rules `S1..Sn` (`blocking` or `minor`, kept by `check: <command>` or by `review`) that `project-check.mjs` parses (`parseStandards`) into `contract.standards` and checks against the profile's commands (a project needs `lint`, and `standards`; `format` is a check). Implementers are shown every rule; every reviewer judges each `review` rule in `standards` (`standards_text`); a broken blocking rule goes back to the spec owning the file (`standards_failures`, kind `standard`), a minor one is reported; `standards_report` gives every rule's status in the result; `standards_problems` stops a run whose tool rule names a check the contract does not have. The file is protected: no run changes it. A criterion QC saw fail goes back to Build like one a reviewer failed (`kind: 'qc'`); `not_observable` passes; `qc: false` turns it off for a change nobody can see. It is the team's own gate, not `pr-judge`: the team must never be tuned to its grader.
- **Models are chosen per role in code.** The `MODEL_TIERS`, `MODELS`, and `MODEL_PROFILES` (`balanced`, `fast`, `flagship`, `orchestrator`, `inherit`, mirrored in `factory/catalog/model-profiles.json`) tables in `factory.py` give each role its Gemini model (balanced defaults: planner `gemini-4-neon-xhigh`, whole-change reviewer & rebuild `gemini-4-neon-high`, implementers/QA/spec reviewers `gemini-4-carbon-medium`, QC `gemini-4-hydrogen-medium`, checker `gemini-4-hydrogen-low`). The `modelProfile` and `models` args accept any Gemini 4 / Orchestrator / Gemini 3.8 model ID or legacy tier alias (`pro`, `flash`, `flash_lite`, `inherit`), which is how to A/B a change before making it the default. If a `run_workflow` runner strictly validates the 4 legacy tier enums, `spawn()` maps concrete model IDs via `workflow_model_tier()` automatically.
- **Skills the team loads are installed, not bundled.** Implementers, QA agents and reviewers read third-party skills with `read_file`, picked by the `SKILLS` registry in `factory.py`: build rows by the spec's `kind`, fixed skills per role (QA: tdd, diagnosing-bugs, verification-before-completion, testing-strategy, mp-code-review, pr-security-review), and a conditional tier with a rule each (vitest, playwright-best-practices, testing-strategy, domain-modeling for implementers; vitest, playwright-best-practices for QA); a run starts without the conditional ones. The README carries a prompt people paste into Gemini Antigravity to install Factory and these skills; keep it in step with the scripts. They are installed into `~/.gemini/config/skills` by `scripts/install-skills.sh` (pinned commits, never overwriting) and resolved before each run by `scripts/skills-ready.sh`, whose `REQUIRED` and `OPTIONAL` lists must match the registry (a test checks it). Do not copy their text into the briefs.
- **Skill, role and script files are in English.** `README.md` is in English too; keep it, and its screenshots in `docs/images/`, in sync when the team, the flow or the layout changes.

## Testing

- **Python workflow & helpers**: the pure helpers in `factory/workflow/factory.py` (`validate_specs`, `build_levels`, `matches_ignore`, `files_outside_ownership`, `files_outside_assignment`, `tests_changed`, `skills_for`, `missing_skills`, `conditional_for`, `MODEL_TIERS`, `MODEL_PROFILES`, `workflow_model_tier`, `model_profile_problems`, `resolve_models_for_profile`, `model_for`, `model_problems`, `evaluate`, `check_failures`, `qc_failures`, `qc_text`, `qc_line`, `route_failures`, `failure_entries`, `run_record`, `spec_text`, `issue_text`, `open_questions`, `questions_text`, `matches_glob`, `protected_files`, `sensitive_kinds`, `assess_risk`, `routed_models`, `escalation`, `scratch_dir`, `needs_browser`, `browser_problem`, `browser_note`, `standards_problems`, `standards_text`, `standards_failures`, `standards_report`, etc.) and the full workflow loop (`run_factory`) are tested in `tests/test_factory_helpers.py` and `tests/test_factory_workflow.py` using `python3 -m unittest discover -s tests -v`. Add a test with every new rule. Both test files load `factory.py` via `compile(..., flags=ast.PyCF_ALLOW_TOP_LEVEL_AWAIT)` so top-level syntax is checked too.
- **ui-refine-loop**: `tests/test_ui_refine_workflow.py` runs `run_ui_refine` whole with `agent`, `parallel`, `phase` and `log` stubbed (stop rules, routing, what each agent is shown, the score); `tests/ui-refine-setup.test.mjs` runs `refine-setup.sh detect`, the helpers of `shoot.mjs` and `pr-shots.sh` against scratch directories, with no dev server and no browser. A real run costs about four agents per round, so confirm with the user first.
- **Setup, skills, and pipeline scripts**: `tests/skills.test.mjs` verifies `skills-ready.sh` against `factory.py`'s registry and scratch skill directories; `tests/project-setup.test.mjs`, `tests/init.test.mjs`, `tests/scan-ui.test.mjs`, `tests/init-status.test.mjs`, `tests/ready-check.test.mjs`, `tests/next-issue.test.mjs`, and `tests/issue-history.test.mjs` run with `node --test`. `factory-issue.sh` calls `gh` only; check it with `bash -n`.
- **pr-judge**: `tests/pr-judge.test.ts` tests the pure helpers of `pr-judge/scripts/lib.ts`. `prepare.ts` and `assemble.ts` need `gh` and a real pull request; a full run starts 8 judge agents, so confirm with the user first.
- **End to end**: copy an eval case's `files/` into a scratch directory, `git init` and commit it, then run `run_workflow` against it. A run starts at least six agents (one spec with tests), and 3N+4 for N specs before any return to Build; each return of a spec to Build adds an implementer and a QA agent, and a return from review adds a checker, the reviewers and QC. Confirm with the user before running more than one.

## Boundaries

- This skill can be symlinked under `~/.gemini/config/skills/factory` or `~/.gemini/antigravity/skills/factory` pointing at the `factory/` folder of this working copy. Every edit here, and every branch switch, changes the skill that sessions using that symlink see, including runs in other projects, which also write `dashboard/live.js` and `dashboard/runs.js` here. The older Factory suite was removed; do not bring it back unless the user asks.
- Untracked and ignored files (for example `factory-workspace/`) are not recoverable through git, so move them to the Trash instead of removing them outright, and look at the target first.
- Commit or push only when the user asks.
